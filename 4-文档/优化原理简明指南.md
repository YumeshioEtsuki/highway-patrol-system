# 系统优化原理 - 简明指南

本文简述公路巡查系统在性能、安全、用户体验方面的优化策略与原理。

---

## 📊 性能优化

### 1. 数据库连接池

**问题**：每次请求都建立新的 MySQL 连接，握手开销大
```
客户端 ━━ TCP 握手 ━━ MySQL ━━ 认证 ━━ SQL 执行 ━━ 结果返回
```

**解决方案**：连接复用（Connection Pool）
```
┌─────────────────────────────────┐
│   应用进程                        │
├─────────────────────────────────┤
│  连接池 (10 个预热连接)           │
│  ┌─────────┬─────────┬─────────┐ │
│  │ Conn 1  │ Conn 2  │ ... ∞   │ │
│  └─────────┴─────────┴─────────┘ │
└─────────────────────────────────┘
         │
         ├─→ 需要连接时，直接从池中取
         └─→ 完成后放回池中（无需断开）
```

**配置**：
```env
DB_POOL_SIZE=10
```

**性能收益**：
- 减少 TCP 握手：~10-50ms / 请求
- 减少 MySQL 认证：~5-20ms / 请求
- 高并发场景下吞吐量提升 **30-50%**

---

### 2. 数据库索引

**问题**：没有索引的查询需要全表扫描
```
SELECT * FROM InspectionRecord WHERE user_id = 123 AND status = 'pending'

扫描方式：
┌─────────────────────────┐
│ 全表扫描 10W 行          │  ← 约 100-500ms
│ 逐行比较 user_id & status │
└─────────────────────────┘
```

**解决方案**：创建复合索引
```sql
-- 为常见查询条件创建索引
CREATE INDEX idx_user_status_time 
  ON InspectionRecord (user_id, status, upload_time);
```

**查询优化效果**：
```
使用索引后：
┌────────────────────────┐
│ B-Tree 索引查询        │  ← 约 1-5ms
│ (user_id, status, ...) │
└────────────────────────┘

性能提升：100~500 倍 ✨
```

**索引策略**：
```
批量导入 → 先删索引
            ↓
        执行 INSERT
            ↓
        重建索引 ← 更快

实时查询 → 创建复合索引
           (常用 WHERE 列)
           ↓
        查询时自动使用
```

### 3. 统计数据缓存

**问题**：每次请求都重新计算统计（COUNT、GROUP BY 等）
```
GET /api/admin/stats
    ↓
SELECT COUNT(*) FROM InspectionRecord...  ← 每次都扫描表
SELECT COUNT(*) WHERE status = 'completed'
...
    ↓
耗时：500ms ~ 2s（取决于数据量）
```

**解决方案**：缓存统计结果（TTL 600s）
```
请求 → 检查缓存
    ↓
  (命中) → 返回缓存    [<5ms]
  (未中) → 查询 DB     [500ms]
         → 保存缓存
         → 返回
    ↓
600s 内重复请求 → 无需重新计算
```

**缓存架构**：
```
┌─────────────────┐
│  Redis (可选)   │  ← 分布式部署下首选
│  性能：<1ms     │
├─────────────────┤
│  内存缓存 (备选) │  ← 单机环保选
│  性能：1-5ms    │
└─────────────────┘
```

**配置**：
```env
REDIS_URL=redis://localhost:6379
STATS_CACHE_TTL=600  # 缓存 10 分钟
```

**性能收益**：
- 缓存命中：减少 99%+ 计算
- 高流量场景下吞吐量提升 **10-100 倍**

### 4. 分页限制

**问题**：未限制的大分页导致大对象序列化、内存溢出
```
GET /api/patrol/list?page=1&page_size=100000

SQL: SELECT * FROM ... LIMIT 100000
     ↓
     分配 100K * 对象大小 的内存
     ↓
序列化为 JSON（可能 100MB+）
     ↓
网络传输（客户端也需处理）
```

**解决方案**：统一限制最大分页
```python
MAX_PAGE_SIZE = 200  # 全局最大每页条数

# 路由中自动夹紧
page_size = min(page_size, settings.MAX_PAGE_SIZE)
```

**性能收益**：
- 防止恶意大分页查询
- 内存占用 → 常数级
- 序列化时间 → 可控

## 🔐 安全优化

### 1. 速率限制（Rate Limiting）

**问题**：无限制的请求可被用于暴力破解、DDoS 攻击
```
暴力破解登录：
POST /api/user/login  ← 每秒 1000 次尝试？
  密码: 123456
  密码: 123457
  ...
```

**解决方案**：基于 IP/用户 限制请求频率
```
登录端点：5 次 / 分钟
  ↓
  6 秒内已达 5 次 → 返回 429 Too Many Requests
  ↓
  60s 后计数器重置

通用字段：
  user:123:login → [时间戳列表]
```

**限制规则**：
```
POST /api/user/login              → 5/min
POST /api/admin/reinit/stream     → 1/min（最危险）
POST /api/admin/generate          → 3/min
POST /api/admin/clean-test-data   → 2/min
```

**性能收益**：
- 防止账户暴力破解
- 防止 DDoS 滥用
- 保护数据库（防止大量无效查询）

### 2. 审计日志

**问题**：无法追踪谁做了什么操作，事后无法调查
```
现象：数据被删除了！
      谁删的？什么时候？为什么？
      → 没有记录，无法查证 ❌
```

**解决方案**：记录所有敏感操作
```sql
CREATE TABLE audit_log (
  id INT PRIMARY KEY,
  user_id INT,           -- 谁做的
  action VARCHAR(50),    -- 做了什么（mark_completed 等）
  resource VARCHAR(100), -- 影响的资源（record:123）
  details TEXT,          -- 详细信息
  timestamp DATETIME     -- 什么时候
);

-- 示例：
INSERT INTO audit_log VALUES (
  1, 5, 'mark_completed', 'record:42', 
  'remark: 已修复路面裂缝', '2025-01-23 14:30:00'
);
```

**应用层集成**：
```python
@router.post("/patrol/{id}/complete")
async def complete_record(id: int, remark: str):
    # 1. 更新记录
    mark_record_as_completed(id, remark)
    
    # 2. 立即记录审计日志
    insert_audit_log(
        user_id=current_user.id,
        action='mark_completed',
        resource=f'record:{id}',
        details=f'remark: {remark}'
    )
    return {"success": True}
```

**审计功能**：
```
后台导出：
  GET /api/admin/audit/export
  ↓
  筛选条件：操作类型、用户、时间范围、关键词
  ↓
  导出 CSV 文件（便于审计、存档）
```

**安全收益**：
- 操作可追踪：谁、什么时候、做了什么
- 事后调查：有据可查
- 合规性：满足审计、监管要求

## 🎨 用户体验优化

### 1. 骨架屏加载

**问题**：数据加载中用户看到空白页，体验感差
```
页面加载：
t=0s   → 页面骨架 ← 瞬间显示
        → 数据加载中...
        ↓
t=0.5s → 空白页面 / 加载圈 ← 用户感觉卡顿
        → 数据...
        ↓
t=2s   → 数据显示 ✓
```

**解决方案**：显示内容的灰色占位符（骨架屏）
```
页面加载：
t=0s   → 表格骨架 + shimmer 动画 ← 瞬间显示
        ↓
        用户感受：哦，在加载数据呢 ✓
        ↓
t=2s   → 真实数据替换占位符 ← 无感知切换
        ↓
        完整的加载流畅体验 ✨
```

**样式实现**：
```css
/* shimmer 动画 */
@keyframes shimmer {
  0%   { background-position: 200% 0; }
  100% { background-position: -200% 0; }
}

.skeleton {
  background: linear-gradient(90deg, 
    rgba(255,255,255,0.05),
    rgba(255,255,255,0.12),
    rgba(255,255,255,0.05)
  );
  animation: shimmer 1.4s infinite;
}
```

**应用位置**：
```
✓ 统计卡片：加载统计数据时
✓ 图表：加载图表数据时
✓ 表格：加载列表数据时
```

**体验收益**：
- 感知加载时间减少 ~40%
- 减少用户焦虑感
- 应用显得更响应迅速

### 2. SSE 自动重连

**问题**：实时推送（SSE）连接断开后无法恢复
```
SSE 连接建立 → 网络波动 → 连接断开
    ↓
    用户看不到实时更新 ✗
    手动刷新页面 ✗
```

**解决方案**：自动重连机制
```javascript
// SSE 连接失败
onerror = () => {
  if (reconnectAttempts < 3) {
    reconnectAttempts++;
    setTimeout(() => {
      console.log('重新连接...');
      startPhotoStream();  // 自动重连
    }, 3000);  // 3秒后重试
  }
}
```

**重连策略**：
```
第 1 次断开 → 等待 3s → 重连
第 2 次断开 → 等待 3s → 重连
第 3 次断开 → 等待 3s → 重连
第 4 次断开 → 放弃，用户手动刷新
```

**体验收益**：
- 网络抖动时无中断
- 用户无需手动刷新
- 实时推送更可靠

## 🏗️ 架构总览

### 优化关键路径
```
请求到来
    ↓
────────────────────────────────────
│ 1. 速率限制检查          (5μs)    │  → 防止滥用
├────────────────────────────────────
│ 2. JWT 认证验证          (10μs)   │  → 安全性
├────────────────────────────────────
│ 3. 数据库查询
│    ├─ 连接池获取          (<1ms)   │  ← 复用连接
│    ├─ 索引查询            (1-5ms)  │  ← B-Tree 加速
│    └─ 结果缓存（可选）    (<1ms)   │  ← 热点数据
├────────────────────────────────────
│ 4. 序列化 JSON            (1-10ms) │
├────────────────────────────────────
│ 5. 审计日志记录           (<5ms)   │  → 追踪操作
└────────────────────────────────────
    ↓
返回响应 (总耗时: 20-100ms)
```
